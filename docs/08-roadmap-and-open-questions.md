# 08 实施路线与待裁定问题

## 1. 路线

| 阶段 | 内容 | 产出 / 验收 |
|---|---|---|
| **0 摸底**(只读) | 用 `parse-list` 把现有协调清单与库匹配;`preflight` 的天线扫描只出统计 | 匹配率;同向/反向/GSO 比例;预计待决天线数 → 决定后续工作量 |
| **1 天线门禁** | 实现来源插件、校验、决策、预检报告;合并两套天线实现 | 全部"已知未处理清单"出现在待决清单中,而不是运行时崩溃 |
| **2 列表与覆盖** | 实现 legacy/user 解析器、规范化、匹配、分类;覆盖应用 | 标准协调表 + 校验报告;覆盖 provenance |
| **3 冻结与批量仿真** | `freeze`、`run`、状态与续跑;适配器接 `X-band-NGSO` | 1 vs N 试点跑通;实测耗时/体积 |
| **4 批量后处理** | `post` 与汇总表 | 跨 pair 汇总、独立重跑 |
| **5 推广** | 全部 200+ 网络分批运行 | 批次审计记录 |

建议先用**一个真实待评估网络**走 0→4 做试点,再推广。

## 2. 验收标准

1. 同一批次内所有 pair `start_utc` 相同;配置写 `TODAY` 必须被拒绝;
2. 对同一波束,不同批次得到字节级相同的曲线(来源+决策一致);
3. 运行期间不得出现"静默回退"日志;任何缺失只出现在待决清单;
4. 中断后重跑,已完成 pair 不重算;
5. 后处理改门限后,只重跑 `post` 即可,raw 无改动(哈希不变);
6. 换机器仅改 `paths.yaml` 与环境变量即可运行。

## 3. 待你裁定的问题

| # | 问题 | 影响 |
|---|---|---|
| Q1 | 待评估网络在每个协调对象里是**只当干扰方**,还是**干扰与受扰两个方向都算**? | pair 数量是否翻倍;`evaluated_role` 取值 |
| Q2 | 图文峰值不一致时默认策略:平移到申报值,还是信任图形? | `shift_to_declared_peak` vs `trust_curve`;`peak_tol_db` 取值 |
| Q3 | 角度不足 180° 时尾部默认策略:`hold_last` / `constant_floor` / 按标准模型远旁瓣? | 是否有全局规则,还是逐波束裁定 |
| Q4 | 来源优先级(特别是 GIMS 矢量、sheet5、位图读图、ITU 模型之间)? | `source_order` |
| Q5 | 仅有峰值增益的 24 个 NGSO 波束、无模型的地球站:是否允许你指定模型,还是排除? | 决策文件内容 |
| Q6 | `DEFERRED_REV_DIR`(反向)是否要在清单里保留并输出? | 报告范围 |
| Q7 | 单个 pair 的可接受耗时与外置盘预留空间? | `max_workers`、缓存策略 |

## 4. 风险

| 风险 | 缓解 |
|---|---|
| 名称匹配歧义多 | 不猜测,裁定持久化;先摸底量化 |
| 待决天线量大 | 允许"按问题码的全局规则",减少逐个裁定 |
| 引擎接口变动 | 全部经适配器,适配器带最小契约测试 |
| 运算/存储超预期 | 阶段 3 先实测再扩大 |
